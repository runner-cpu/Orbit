# 轨道之上：一片正在增厚的碎片带

> Above the Orbit: A Thickening Shell of Debris

2026 年第十四届全国大学生数字媒体科技作品及创意竞赛 · 智慧教育与科普创作类赛项参赛作品。

一个纯静态的 Web 交互叙事长页：把近地轨道上的真实编目对象逐一画出来，
用可拖动的时间轴展示碎片在特定高度层持续增厚的过程。所有位置由 SGP4
在浏览器里现场解算，不是预渲染视频，也不是贴图动画。

**线上地址**：https://runner-cpu.github.io/Orbit/

---

## 全五章已完成

| 章 | 问题 | 用到的数据 |
|:---|:---|:---|
| 一 现在头顶上有多少东西 | 编目里有多少、能定位多少 | SATCAT + GP 根数 |
| 二 数量不是线性增长 | 增长由哪几次事件顶上去 | SATCAT 逐年增量 |
| 三 风云一号C | 碎片停在了哪个高度层 | 2,676 个碎片点云 |
| 四 一次真正的碰撞 | 两个碎片云为什么不在同一个面 | 碎片点云 + 倾角 |
| 五 它们会自己掉下来吗 | 各高度层的清除时标与外推 | 编目自身拟合 |

全片用一条滚动叙事串起来：左侧是文字，右侧是同一个三维场景，
相机与图层参数由一个共享的场景表驱动，章与章之间不重置视角。

## 技术底座

| 项 | 内容 |
|:---|:---|
| 技术栈 | Vite + TypeScript + three.js + satellite.js（均为 MIT 许可） |
| 数据来源 | CelesTrak 公开的 SATCAT 编目与 GP 轨道根数 |
| 数据历元 | 2026-10-13T00:00:00Z（固定，不跟随系统时间） |
| 运行要求 | 零后端、零运行时网络依赖，断网可完整运行 |
| 产物 | 纯静态文件，可放在任意子路径下 |

数据历元固定这一点很重要：TLE 的精度随时间衰减，若页面跟随「今天」解算，
不同日期打开会得到不同结果。评审在赛程后段打开时，看到的必须是与提交时
一致的那一版。

## 本地运行

```bash
npm ci          # 按 lockfile 安装，保证与线上构建一致
npm run dev     # 开发服务器 http://127.0.0.1:5173
npm run build   # 类型检查 + 构建到 dist/
npm run preview # 预览构建产物
```

数据已经随仓库提交，克隆后不需要重新下载即可直接构建。

### 重新生成数据

原始数据在 `data/raw/`，成品在 `public/data/`。如需更新到更新的编目：

```bash
npm run satcat        # 取 CelesTrak SATCAT 编目，重算在轨构成
npm run merge         # 合并去重 GP 轨道根数
npm run runtime-data  # 构建期解算，输出 catalog.bin 与 debris.bin
npm run history       # 从编目本身拟合增长序列与衰减时标，输出 history.json
npm run coastlines    # 提取 Natural Earth 海岸线
npm run verify        # 核对页面上每一个读数
```

`npm run verify` 有 51 项断言，覆盖编目条数、分类口径、高度分布求和、
碎片群统计、逐点近地点与倾角、碎片与编目去重、海岸线坐标范围。
页面上的每个数字都能由它从原始数据复现。
CI 在构建前会先跑这一步，数字对不上就不会发布。

## 目录结构

```
src/
  core/       引擎层：地球、点云、相机、滚动叙事、数据加载
  content/    内容层：文案、图表、方法说明。所有数字来自 figures.ts
  chapters/   场景驱动：scenes.ts 是全五章共用的唯一场景表
scripts/      数据处理与校验脚本
data/raw/     原始数据（TLE 与 SATCAT CSV）
public/data/  运行时数据成品（catalog.bin、debris.bin、history.json 等）
docs/         参赛方案、参考网页技术分析、逐章验证截图
```

三层的耦合点只有「步骤标识」这一个字符串：文案层声明每一步要什么镜头，
场景层负责翻译成具体参数，主循环不参与内容决策。

### 场景表为什么是共用的

五个章节的相机状态是连续的——从第一章的远景推进到第三章的碎片壳，
再拉回到第五章的全球视角，中间不能有跳变。如果每章各自维护相机状态，
章与章交界处一定会出现「上一章的位置被重置」这种断点。

因此全部镜头状态集中在一张表里（`src/chapters/scenes.ts`），
一个场景只需声明与上一个场景不同的字段，其余字段沿继承来。
这样新增一章只是往表里追加若干条，不需要改动任何已有场景。

### 为什么第五章要分成两个场景

`decay-observe` 与 `decay-project` 用同一个视角、同一个图层，唯一区别是
后者会把时间推进。这不是冗余：如果观测结论与外推共用一帧画面，
观众无法分辨哪些是已经发生的事、哪些是模型的产物。
把两者拆开后，「时间开始流动」这件事本身就成了一个可见的叙事动作。

## 两个数据集，两种用途

页面上同时用到两份数据，口径不同，各负责一类结论：

- **SATCAT（卫星编目）**回答「有多少」。它覆盖全部编入册的目标（含已再入），
  据此得出在轨总数 35,328 个、其中正在工作的载荷 16,801 个。
- **GP 轨道根数**回答「在哪里」。它只维护其中一部分，本项目能解算出位置的
  有 15,934 个。

两者的差 19,407 个是一个结论本身，不是数据缺陷：公开根数只维护还有人在用的
对象，大量碎片与火箭残骸没有在工作的发射方，也就没人更新根数。
页面把这一点作为「这一页画出的景象偏乐观」的依据写了出来，而不是隐去。

## 已实现的关键工程决策

**惯性系转地固系。** TLE 给出的位置在惯性系里，地球在自转。若不做转换，
点云会相对地理参照物持续漂移。构建期按历元的 GMST 绕 Z 轴旋转一次，
之后点云就固定在地固系中，可以直接叠在地球与海岸线上。

**构建期解算与运行期筛选分工。** 全部 18,610 条根数（15,934 个编目对象 +
2,676 个碎片）都在构建期用 SGP4 解算一次，各自写成 Float32Array 二进制：
`catalog.bin` 是 stride 7（位置 + 四个类别字段），`debris.bin` 是 stride 7
（位置 + 近地点 + 远地点 + 倾角 + 所属事件）。页面只做两次上传，
运行期不跑 SGP4，因此滚动与拖动都只改 uniform，不产生计算尖峰。

碎片之所以要逐点保留近地点与倾角，是因为第三、四章按这两个量筛选：
第三章只显示近地点落在某一区间的碎片，第四章把两个碎片云按倾角分开着色。
这些筛选全部在顶点着色器里完成（见下一条）。

**着色器里查类别表。** 切换「单色 / 按类别着色 / 只看某一类」只改 uniform，
不重新上传上万条颜色数据。

**筛选也只改 uniform，不重建几何。** 第二章按年份、第三四章按高度或倾角、
第五章按时间推进，三种筛选都是把不可见的点推到裁剪空间外并置 `gl_PointSize = 0`
（`vec4(2.0, 2.0, 2.0, 1.0)`），而不是 `discard` 或重建缓冲区。
不用 `discard` 是因为它在部分驱动上会关掉 early-z 并导致明显的帧率波动；
推到裁剪空间外是各驱动行为一致的做法。副作用是点数不变、只有可见性变化，
所以「渲染对象」这个读数在整个第二至五章保持恒定，这也是设计意图。

**碎片寿命是确定性的，不是随机的。** 第五章的时间外推需要给每个碎片一个
「第几年消失」。若每帧现算随机数，拖动滑块时画面会闪烁。
做法是在启动时用整数哈希 `hash01(index)` 取一个固定的均匀分布样本 u，
再按该碎片所在高度层的实测时间常数求 `t = −τ·ln(u)`。
同一个碎片在任何一帧、任何一次重拖下都得到同一个寿命。

**区分惯性坐标与渲染坐标。** `updateFromEcef` 负责坐标系重排，
数据层不感知 three.js 的轴约定。

## 视觉约定

整页锁定单一深色主题。颜色分两类且职责不重叠：

- **结构色**（网格、边框、刻度）只划分信息层级，不携带语义；
- **数据色**（强调青与五个类别色）只用于编码数据，不做装饰。

类别的含义在页面上有对应图例，不靠观众猜测。四个类别的颜色同时满足
色觉障碍可分辨性要求（亮度差而非仅色相差）。

## 已知限制

这些限制在页面的「数据与方法」一节中也对观众写明：

- 只能画出有公开轨道根数的对象，画不出的那些恰是碎片环境的主体；
- 编目条数本身随时间变化，不同历元的数字不可直接比较；
- 轨道根数只在历元附近有效，本作固定使用 2026-10-13 的历元；
- 不提供交会预警或机动信息，这超出科普作品的范围。

中文正文回落系统字体栈。一套中文字体的子集化文件仍在数百 KB 量级，
在「零外部依赖、体积可控」的前提下不做随包分发，这一点也在方法页写明。
